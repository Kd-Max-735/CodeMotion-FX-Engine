# glitch_slice 自检规则

## 输入契约

- 自检 JSON 顶层只有 `file_name`、`original_request`、`summary`、`metadata`。
- 画面证据只有最终 MP4 生成的 `keyframe_contact_sheet`。
- 所有结论必须来自最终成片，不引用源图或中间结果。

## 核心原则

故障切片的目标是让成组横条或竖条发生可辨认的整体错位，可伴随有限彩色边缘。切片撕裂是正常故障视觉；只有视频无法完整解码或抽取预定关键帧失败，才属于技术故障。

## 自检视图字段及含义

- `file_name`：安全文件名。
- `original_request`：用户要求的方向、粗细、密度、强弱和彩色边缘偏好。
- `summary.description`：描述实际切片方向、错位程度和完成状态。
- `summary.key_information`：记录切片方向、错位可见度和后段完整性。
- `metadata.media`：成片媒体事实与完整解码结果。
- `metadata.quality`：技术完整性及关键帧读取情况。
- `metadata.effect_observation`：切片结构、时间变化和完成观察。
- `metadata.keyframe_evidence`：切片初现、结构、变化和后段画面的时间证据。

## 关键帧证据检查方法

检查切片初现、稳定结构、错位变化与后段切片。横向切片应表现为条带左右错位，纵向切片应表现为列块上下错位。抽帧数量随片长自动调整，并按时间合成一张联系表。

## 用户要求到证据的映射

| 用户要求 | 证据 |
| --- | --- |
| 横向或纵向切片 | 切片结构与错位变化画面 |
| 细碎或粗大 | 条带/列块的可见尺度 |
| 轻微或强烈撕裂 | 错位覆盖范围及多个时刻的变化 |
| 要或不要彩色边 | 切片边缘的颜色分离表现 |
| 后段仍保持故障 | 后段关键帧 |

## 判定流程

1. 提取用户明确提出的方向、尺度、强弱和边缘风格。
2. 确认联系表呈现成组切片，而不是随机噪点或跨帧残留。
3. 对照各时刻检查错位变化和后段状态。
4. 技术完整性只按解码与读取证据判断。

## 通过与返修原则

切片结构、方向和强弱满足用户要求且技术检查通过时通过。返修意见只描述可见差异，例如“应改为纵向列块”“切片过细”“彩色边缘不应出现”。

## 禁止事项

- 不把切片撕裂、红蓝边、整条错位或快速跳变判成编码损坏。
- 不输出参数、种子、公式、算法、后端或资源信息。
- 不把数据错帧、像素排序或随机噪点当作切片通过证据。
- 不增加用户没有提出的故障强度要求。
